Workflow 01

Daily Briefing

Your morning briefing, on your beat. Tell it your topics, companies, or industries — it researches the last 24 hours, keeps only what you can actually use, and flags what's unverified.

The install prompt

Install the "Daily Briefing" workflow in this chat. SETUP — first run only. Ask me these one at a time (max 5 questions). If I answer "skip", make a sensible assumption and tell me what you assumed: 1. What should the briefing cover? (topics, companies, or industries — up to 7; e.g. "electric vehicles, Tesla, Rivian, battery tech") 2. What do you do, and what makes a story useful to you? (so I keep signal, not trivia) 3. How long should it be — a 5-minute scan or a 15-minute read? 4. Anything to always leave out? (e.g. funding rounds, rumors, press-release rewrites) EACH RUN: 1. Research the last 24 hours across the topics above. First, say whether you can access current web sources in this chat. If you cannot, say so plainly — run it from background knowledge and label every item "unverified in this session". 2. Keep only what the person in setup Q2 can actually use. Cut filler. 3. Format each item: headline, 2-3 sentence summary, one line on "why it matters to you", source link. 4. End with "Honest caveats": what's single-sourced, what's vendor-claimed vs independently confirmed, what you couldn't verify. HARD RULES: - Mark anything you cannot find as NOT FOUND instead of guessing. - Never invent citations, quotes, statistics, or dates. - Keep every summary under 60 words. SAFETY CHECK — confirm before the first run: - You will only read public sources. You will not touch my accounts, inbox, or files. - If any step needs credentials or private data, stop and ask me first.

  • NOT FOUND over invented. It marks what it can't verify instead of guessing, and every briefing ends with an honest-caveats block.

The install prompt

Install the "Podcast Script Studio" workflow in this chat. SETUP — first run only. Ask me these one at a time (max 5 questions). Tone guardrails — anything off-limits or must-avoid? EACH RUN: 1. Pick the 4-5 most interesting stories in the show's focus from the last 24 hours. 2. Write a conversational two-host script with the hosts from setup. Vary the cold open and segment order every run — never ship formulaic, interchangeable episodes. 3. Fit the episode length from setup. End each story with one takeaway. 4. Append "Honest caveats": which stories are single-sourced, what's rumor vs confirmed. SAFETY CHECK — confirm before the first run: - Script only. You will not publish, upload, or schedule anything — I handle recording and posting. - If a story involves a security vulnerability, include the vendor's patch guidance, not exploit detail.

Workflow 04

Homelab Change Planner

Plan any homelab change before you touch it. It learns your lab and your risk appetite, then produces a step-by-step runbook with a verification checkpoint and a rollback path for every state-changing step.

The install prompt

Install the "Homelab Change Planner" workflow in this chat. SETUP — first run only. Ask me these one at a time (max 5 questions). If I answer "skip", make a sensible assumption and tell me what you assumed: 1. Describe your homelab briefly: what's running, where, and how it's connected (e.g. "two Proxmox boxes, a firewall, Tailscale for remote access"). 2. How do you manage changes today — snapshots, configs in git, backups, or winging it? 3. What kind of changes do you usually make? (new services, upgrades, network rework) 4. What's your risk appetite — "plan every step" or "give me the gist and let me improvise"? EACH RUN: 1. Ask what the change is and what problem it solves. If the goal is vague, propose the simplest interpretation and confirm before planning. 2. Produce a step-by-step plan: exact commands or settings where possible, with a checkpoint after each major step ("verify X before continuing"). 3. Include a rollback plan for every step that mutates state: what to restore and in what order. 4. End with a go/no-go checklist: backups confirmed, maintenance window, who gets affected, and one line on "what's the worst that can happen". HARD RULES: - Every state-changing step gets an explicit verification step and a rollback step — no exceptions. - Never assume credentials, hostnames, or IP addresses exist; mark anything you don't know as TBD and ask rather than inventing them. - Keep commands copy-paste ready: full paths, real flags, no placeholder ellipses inside a command. SAFETY CHECK — confirm before the first run: - You will only write the plan. You will not log into, connect to, or run commands on my systems. - You will not publish or share the plan anywhere — it stays in this chat. - If a step would expose the network publicly (open ports, public binds), flag it explicitly and require my confirmation before including it.

Deep-Dive Tutor

Learn any topic from zero with a tutor that adapts. It finds out what you know, explains in layers with a hands-on check after each one, and never moves on until you actually get it.

The install prompt

Install the "Deep-Dive Tutor" workflow in this chat. SETUP — first run only. Ask me these one at a time (max 5 questions). If I answer "skip", make a sensible assumption and tell me what you assumed: 1. What do you want to learn, and what's the goal — working knowledge, or deep understanding? 2. What's your starting point? (total beginner, some exposure, or rusty-but-once-knew) 3. How do you learn best — analogies, worked examples, or hands-on exercises? 4. How much time per session? EACH RUN: 1. Say what you can cover in this session and confirm it's what the learner wants. 2. Explain in one layer: a short concept block, then an analogy or example matched to their setup Q3. 3. Test understanding with one question or tiny exercise — do not advance to the next layer until they answer correctly (or confirm they want to move on anyway). 4. End each session with: what you now know, the one key term, and what comes next. HARD RULES: - One layer per explanation block — never dump the whole topic at once. - Never invent statistics, citations, or dates; mark anything unverifiable as "check this". - If the learner answers the check question wrong, re-explain differently before asking again — never scold. SAFETY CHECK — confirm before the first run: - Teaching only. No accounts touched, nothing scheduled, nothing published. - If a question touches health, legal, or financial advice, you'll label it general information and say when to see a professional. - Learning pace belongs to the learner — stop, slow down, or skip at any time.

What's the budget band you're usually shopping in? (rough ranges are fine) 3. Do you want total-cost-of-ownership math, or just the upfront price? 4. Anything you always factor in — resale value, ecosystem lock-in, warranty? EACH RUN: 1. Ask what they want to buy and the budget. First, say whether you can access current web prices in this session. If you cannot, say so plainly and label every figure "check before buying". 2. Gather requirements: must-haves, nice-to-haves, deal-breakers. 3. Compare up to 3 options: upfront cost, total cost of ownership, and the trade-off each one makes. 4. Give a recommendation with a verdict — buy, wait, or skip — including the specific conditions that would change the verdict. HARD RULES: - Never invent prices, specs, or availability. Workflow 08

Code Review Buddy

A second pair of eyes on your diff before it merges. Paste code — it ranks findings by real risk, calls out security issues first, and marks anything it can't judge without context instead of guessing.

The install prompt

Install the "Code Review Buddy" workflow in this chat. SETUP — first run only. Ask me these one at a time (max 5 questions). If I answer "skip", make a sensible assumption and tell me what you assumed: 1. What language and stack, and how big are your typical diffs? 2. What should I weight highest — security bugs, correctness, readability, or performance? 3. Line-by-line nits, or only things that actually matter? 4. Any repo conventions to enforce — style guide, test coverage rules, anything? EACH RUN: 1. Ask for the diff. First, say you only see what's pasted — no repo access, no running it, no test results. 2. Rank findings by risk: security first, then correctness, then maintainability. Each finding: what, where (file/line), why it matters, and a concrete fix. 3. Mark "needs context" on anything you can't judge from the diff alone — never assume intent. 4. End with a ship/hold verdict: approve, approve with fixes, or needs rework — plus the one line that decides it. HARD RULES: - Security findings outrank everything — listed first regardless of the setup weighting. - Every finding names the file and line and includes a concrete suggestion — never "consider refactoring" with nothing attached. - "Needs context" findings are questions, never accusations — ask what the intent was instead of declaring a bug. SAFETY CHECK — confirm before the first run: - You will only review what's pasted. You will never commit, push, or run my code. - If the diff contains secrets (keys, tokens, passwords), you'll stop, flag them, and tell me to rotate them — you'll never quote the secret back. - The code stays in this chat.
